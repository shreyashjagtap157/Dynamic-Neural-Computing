# DNC-IR: Intermediate Representation Specification

**Date**: 2026-07-22  
**Status**: SPECIFICATION  
**Depends on**: Foundational Baseline Freeze (Q1–Q5)  
**Depended on by**: Mutation Semantics, Transaction Semantics, Dynamic Computation Control Layer

---

## 1. Purpose and Scope

### 1.1 What DNC-IR Is

**DNC-IR is the canonical intermediate representation of a DNC computational structure, including its computational units, relationships, execution-relevant constraints, state bindings, capabilities, and structural metadata.**

DNC-IR is the language in which DNC computational structure is described. It provides the semantic boundary between dynamic computation generation and execution.

### 1.2 What DNC-IR Is Not

| DNC-IR Is | DNC-IR Is Not |
|-----------|---------------|
| Structural description of computation | Execution trace |
| Canonical graph representation | Runtime state snapshot |
| Mutation target format | Learning model |
| Serialization-independent semantics | Provider-specific representation |
| Constraint-expressible structure | Hardware-specific IR |

### 1.3 Design Principles

1. **Semantics before syntax**: The meaning of DNC-IR is defined before its representation.
2. **Structure is primary**: DNC-IR describes *what computation exists*, not *how it executes*.
3. **Mutation-aware**: DNC-IR operations are designed for structural mutation, not just static description.
4. **Identity-stable**: Every element has stable identity across mutations and versions.
5. **Constraint-expressible**: DNC-IR can express the constraints that structural mutations must satisfy.
6. **Serialization-agnostic**: The semantic model is independent of any particular serialization format.

## 2. Relationship to Σ(t)

### 2.1 Position in System State

DNC-IR represents the **structural component** of the Computation Domain, not the entire Computation Domain:

```
Σ(t)
│
├── Execution Domain
│       working_memory, history, checkpoints, cost
│
├── Computation Domain
│       │
│       ├── Structural Component
│       │       └── DNC-IR Structural Graph (canonical representation)
│       │
│       ├── Unit State
│       │       Runtime state of ComputationalUnits
│       │       (parameters, internal buffers, execution status)
│       │
│       └── Registry
│               ModuleType → Contract mapping
│
└── Adaptation Domain
        learning_state, memory, adaptation_history
```

**What graph does Σ(t) contain?** Σ(t) contains the **Structural Graph** — the canonical DNC-IR representation. The Execution Core projects this to an **Executable DAG** for execution. The Structural Graph may be more expressive than a DAG; the Executable Graph is always a DAG.

Note: Q3 describes the Computation Domain as containing "graph: Graph, Current DAG of ComputationalUnits." This was written before the Structural/Executable distinction was introduced. The correct interpretation is: Σ(t) contains the Structural Graph; the Execution Core uses a DAG projection for execution.

### 2.2 Why Not the Entire Computation Domain

DNC-IR does not represent:

- **Unit State**: The runtime state of individual units (parameters, internal buffers) lives outside DNC-IR. DNC-IR describes the structure; unit state is managed by the Execution Core.
- **Registry**: The module type registry is separate from the graph structure. DNC-IR references types; the registry defines them.

### 2.3 What DNC-IR Represents

DNC-IR represents:

- The graph of ComputationalUnits (nodes and edges)
- The identity and properties of each unit
- The relationships between units
- The constraints that the structure must satisfy
- The capabilities that each unit exposes for mutation
- The version history of the structure

## 3. Graph Model

### 3.1 Structural Graph vs. Executable Graph

DNC-IR distinguishes two levels of graph expressiveness:

```
DNC-IR Structural Graph
    The full expressiveness of DNC-IR
    May represent recurrent structures, feedback, iterative patterns
    Used for: design, analysis, mutation planning, storage

Executable Graph
    A DAG-constrained projection of the Structural Graph
    Used for: actual execution by the Execution Core
    Generated by: lowering the Structural Graph
```

**The executable DNC-IR must be acyclic.** But DNC-IR itself may represent more expressive structures. This distinction enables:

- Representing recurrent computation as a structural pattern (unfolded at execution time)
- Modeling feedback loops conceptually (lowered to iterative execution)
- Storing non-DAG structures for analysis and mutation planning

### 3.2 Graph Definition

```
Graph
│
├── identity
│       graph_id: GraphID (globally unique, stable across mutations)
│       version: GraphVersion (monotonically increasing)
│       name: str (human-readable)
│
├── structure
│       units: Dict[UnitID, ComputationalUnit]
│               All computational units in the graph
│
│       edges: List[Edge]
│               Connections between units
│
├── boundary
│       entry_points: List[PortRef]
│               External inputs to the graph
│
│       exit_points: List[PortRef]
│               External outputs from the graph
│
├── constraints
│       structural: Set[StructuralConstraint]
│               Constraints on graph structure
│
└── metadata
        created_at: Timestamp
        mutation_history: List[MutationID]
                IDs of mutations that produced this version
        provenance_hash: Hash
                Tamper-evident hash of the graph structure
```

### 3.3 Graph Properties

| Property | Requirement | Rationale |
|----------|-------------|-----------|
| Identity | Every graph has a stable GraphID | Enables provenance tracking across mutations |
| Versioning | Every mutation increments GraphVersion | Enables version-specific queries |
| Acyclicity | The executable projection must be a DAG | Required by Execution Core (INV-3) |
| Boundary | Every graph has explicit entry/exit points | Enables composition and subgraph extraction |
| Constraints | Every graph carries its structural constraints | Enables validation after mutation |

## 4. ComputationalUnit Representation

### 4.1 The Three Orthogonal Dimensions

Every ComputationalUnit is defined by three independent dimensions (from Q2):

```
ComputationalUnit
│
├── identity
│       unit_id: UnitID (globally unique, stable)
│       name: str (human-readable)
│
├── dimensions
│       structure: PRIMITIVE | COMPOSITE
│       visibility: OPAQUE | INSPECTABLE
│       lifecycle: BASE | SPECIALIZED
│
├── interface
│       inputs: List[InputPort]
│       outputs: List[OutputPort]
│
├── contract
│       preconditions: Set[Condition]
│       output_contract: OutputContract
│       cost_estimate: CostEstimate
│
├── capabilities
│       mutation_capabilities: MutationCapabilitySet
│               What mutations are permitted on this unit
│
└── metadata
        version: Version
        created_by: MutationID
        description: str
```

### 4.2 Dimension Values

#### Structure Dimension

| Value | Meaning | Internal Structure |
|-------|---------|-------------------|
| `PRIMITIVE` | Atomic; cannot be decomposed | None |
| `COMPOSITE` | Contains internal units and edges | `internal_units`, `internal_edges` |

#### Visibility Dimension

| Value | Meaning | Mutability |
|-------|---------|------------|
| `OPAQUE` | Implementation hidden; black box | Cannot be partially mutated |
| `INSPECTABLE` | Internal structure visible | Can be partially mutated |

#### Lifecycle Dimension

| Value | Meaning | Origin |
|-------|---------|--------|
| `BASE` | Normal unit | Created by user or Generator |
| `SPECIALIZED` | Consolidated reusable unit | Created by DNC-6 consolidation |

### 4.3 Derived Roles

Common dimension combinations produce recognizable semantic roles:

| Role | Structure | Visibility | Lifecycle |
|------|-----------|------------|-----------|
| Primitive | PRIMITIVE | INSPECTABLE | BASE |
| Module | (any) | OPAQUE | BASE |
| Composite | COMPOSITE | INSPECTABLE | BASE |
| Subgraph | COMPOSITE | OPAQUE | BASE |
| Specialized | (any) | (any) | SPECIALIZED |

These are **derived roles**, not fundamental types. The fundamental identity is the three dimensions.

## 5. Relationships (Edges)

### 5.1 Edge Definition

```
Edge
│
├── identity
│       edge_id: EdgeID (globally unique, stable)
│
├── connection
│       source: UnitRef (unit_id + port_id)
│       target: UnitRef (unit_id + port_id)
│
├── properties
│       data_type: DataType (what flows through this edge)
│       optional: bool (whether this connection is required)
│       weight: float (optional; for weighted connections)
│
└── metadata
        created_by: MutationID
        version: Version
```

### 5.2 Edge Types

| Type | Meaning | Example |
|------|---------|---------|
| `DATA` | Data flows from source to target | Output of one unit feeds input of another |
| `CONTROL` | Control flow dependency | One unit must complete before another starts |
| `CONDITIONAL` | Data-dependent routing | Edge is active only when condition holds |

### 5.3 Edge Constraints

Every edge must satisfy:

1. **Source exists**: The source unit and port exist in the graph
2. **Target exists**: The target unit and port exist in the graph
3. **Type compatibility**: Source output type matches target input type
4. **No self-loop**: An edge cannot connect a unit to itself
5. **No duplicate edges**: At most one edge between any (source_port, target_port) pair

## 6. Identity Semantics

### 6.1 Identity Types

| Identity | Scope | Lifetime | Mutability |
|----------|-------|----------|------------|
| `GraphID` | Global | Permanent | Immutable |
| `GraphVersion` | Per-graph | Per-mutation | Monotonically increasing |
| `UnitID` | Global | Permanent (until removed) | Immutable |
| `EdgeID` | Global | Permanent (until removed) | Immutable |
| `PortID` | Per-unit | Permanent | Immutable |
| `MutationID` | Global | Permanent | Immutable |

### 6.2 Identity Stability

**UnitID is stable across mutations.** When a unit is added, it receives a UnitID. When it is removed, the UnitID is retired but never reused. When a unit is replaced, the new unit receives a new UnitID.

This means:

- "What unit was at position X at version V?" is always answerable.
- "What mutations affected unit U?" is always answerable.
- "What was the graph structure at version V?" is always answerable.

### 6.3 Identity and Provenance

Every identity is created by a mutation. The `created_by` field links identity to provenance:

```
Graph G (GraphID: g1)
    Version 17
        Mutation M42
            creates Unit U91
            creates Edge E103
            creates Port P201 on U91
```

This enables full provenance reconstruction: given any element, we can trace back to the mutation that created it.

## 7. Version Semantics

### 7.1 Graph Versioning

Every mutation increments the graph version:

```
Version 0: Initial graph
    Mutation M1 → Version 1
    Mutation M2 → Version 2
    Mutation M3 → Version 3
    ...
```

### 7.2 Version Immutability

A specific version is immutable. Version 17 is always the same graph. To "modify" version 17, you create version 18.

### 7.3 Version Queries

| Query | Answer |
|-------|--------|
| "What is the current version?" | Latest GraphVersion |
| "What was the graph at version V?" | Checkpoint at version V |
| "What changed between V1 and V2?" | Diff of units and edges |
| "What mutation produced version V?" | MutationID in version metadata |

### 7.4 Version and Mutation History

The mutation history is append-only:

```
mutation_history: [M1, M2, M3, ..., M42]
```

Each mutation records:
- What was added, removed, or changed
- Which version it produced
- The provenance hash

## 8. Contracts

### 8.1 Unit Contract

Every ComputationalUnit exposes a formal contract:

```
UnitContract
│
├── InputContract
│       required_inputs: List[InputSpec]
│               Name, type, whether optional
│
├── OutputContract
│       outputs: List[OutputSpec]
│               Name, type, guarantees
│
├── StateContract
│       stateful: bool
│       state_type: Optional[TypeSpec]
│       state_persistence: EPHEMERAL | CHECKPOINTED | PERSISTENT
│
├── ResourceContract
│       cost_estimate: CostEstimate
│       memory_estimate: Optional[MemoryEstimate]
│       latency_estimate: Optional[LatencyEstimate]
│
├── ExecutionContract
│       deterministic: bool
       idempotent: bool
       max_execution_time: Optional[Duration]
│
└── MutationContract
        may_be_added: bool
        may_be_removed: bool
        may_be_rewired: bool
        may_be_specialized: bool
        may_be_consolidated: bool
        may_be_composed: bool
        may_be_split: bool
        may_be_merged: bool
        may_be_decomposed: bool
```

### 8.2 The Mutation Contract

The MutationContract gives structural mutation a formal **capability model**. It defines what is *technically permitted* for this unit, independent of what is *currently authorized* (Controller) or *preferred* (Policy):

| Capability | Meaning | Operation |
|------------|---------|-----------|
| `may_be_added` | This unit type can be added to a graph | AddUnit |
| `may_be_removed` | This unit type can be removed from a graph | RemoveUnit |
| `may_be_rewired` | This unit's edges can be modified | Connect, Disconnect, Rewire |
| `may_be_specialized` | This unit can become SPECIALIZED lifecycle | Specialize |
| `may_be_consolidated` | This unit can participate in consolidation | Consolidate |
| `may_be_composed` | This unit can be grouped into a COMPOSITE | Compose, ExtractComposite |
| `may_be_split` | This unit can be split into smaller units | Split |
| `may_be_merged` | This unit can be merged with other units | Merge |
| `may_be_decomposed` | This COMPOSITE unit can be flattened | Decompose, InlineComposite |

**Capability ≠ Authorization ≠ Policy:**

| Concept | Definition | Authority |
|---------|------------|-----------|
| **Capability** | What is technically permitted (MutationContract) | Unit declaration |
| **Authorization** | What is currently approved | Structural Controller |
| **Policy** | What is preferred or allowed | Generator / system configuration |
| **Constraint** | What is conditionally required | Validation pipeline |

The Mutation Engine checks capabilities first (does the unit allow this?), then the Controller checks authorization (should this be approved?), then the validation pipeline checks constraints (does this satisfy requirements?). This prevents the Engine from arbitrarily modifying units that declare certain operations prohibited.

### 8.3 Contract Validation

Contracts are validated:

1. **At unit creation**: The unit's contract must be satisfiable
2. **At edge creation**: The source output must match the target input contract
3. **At mutation**: The mutation must not violate any contract
4. **At execution**: The Execution Core verifies preconditions before execution

## 10. Constraints

### 10.1 Constraint Types

```
Constraint (abstract)
│
├── StructuralConstraint
│       DAGConstraint: No cycles in the executable projection
│       ConnectivityConstraint: All units must be reachable from entry points
│       BoundaryConstraint: Entry/exit points must exist
│
├── TypeConstraint
│       TypeCompatibility: Source output type matches target input type
│       PortTypeConstraint: Port types must be valid
│
├── ResourceConstraint
│       CostConstraint: Total cost ≤ budget
│       MemoryConstraint: Total memory ≤ budget
│       LatencyConstraint: End-to-end latency ≤ bound
│
├── DependencyConstraint
│       PreconditionConstraint: Unit preconditions must be satisfiable
│       OrderingConstraint: Execution order must respect dependencies
│
├── MutationConstraint
│       IdentityStability: UnitIDs must not change after creation
│       VersionMonotonicity: GraphVersion must increase
│       ProvenanceIntegrity: Provenance hash must be consistent
│
└── SafetyConstraint
        NoPartialState: Mutations must not leave partial state visible
        NoSilentFailure: Mutations must not fail silently
        NoUncheckedMutation: Mutations must be validated before application
```

### 10.2 Constraint Scope

| Scope | Applies To | Enforced By |
|-------|------------|-------------|
| Graph-level | Entire graph | Structural Controller |
| Unit-level | Individual unit | Unit contract |
| Edge-level | Individual edge | Type constraints |
| Mutation-level | Specific mutation | Mutation Engine |

## 11. Invariants vs. Constraints vs. Policies

### 11.1 Definitions

| Concept | Definition | Violation |
|---------|------------|-----------|
| **Invariant** | Must always hold. Cannot be violated under any circumstances. | System error; rollback required |
| **Constraint** | Must hold for a particular structure or operation. May be relaxed under specific conditions. | Mutation rejected or modified |
| **Policy** | Determines what is preferred or allowed. Not mandatory. | Warning; logged but not rejected |

### 11.2 Examples

| Type | Example | Enforcement |
|------|---------|-------------|
| Invariant | "The graph must be acyclic" | Always enforced; violation = error |
| Invariant | "History is append-only" | Always enforced; violation = error |
| Constraint | "Total cost ≤ budget" | Enforced at mutation time; may be relaxed with authorization |
| Constraint | "Type compatibility across edges" | Enforced at edge creation; may be modified by Controller |
| Policy | "Prefer composites over flat graphs" | Logged; not enforced |
| Policy | "Avoid duplicate computation" | Warning; may be overridden |

### 11.3 Why This Distinction Matters

The distinction becomes critical when the Mutation Engine evaluates a proposal:

1. **Invariant violation**: Reject immediately. No modification possible.
2. **Constraint violation**: Reject or modify. Controller may adjust the proposal.
3. **Policy violation**: Log warning. Controller may override if justified.

This prevents the Controller from treating all violations equally. Invariants are absolute; constraints are negotiable; policies are advisory.

## 12. Abstract IR Operations

### 12.1 Operation Categories

DNC-IR operations are **abstract transformations** on the graph. They are not mutations (which are proposed, authorized, and applied transactionally). They are the *vocabulary* of mutation.

```
Graph Operations
│
├── Structural Operations
│       CreateGraph
│       AddUnit
│       RemoveUnit
│       ReplaceUnit
│
├── Connection Operations
│       Connect
│       Disconnect
│       Rewire
│
├── Composition Operations
│       ExtractComposite
│       InlineComposite
│       Split
│       Merge
│
├── Lifecycle Operations
│       Specialize
│       Deprecate
│       Archive
│
└── Analysis Operations (READ-ONLY)
        Validate
        Inspect
        Diff
        Query
```

**Note**: Analysis Operations are **read-only queries** on the graph. They do not modify state, do not require authorization, and do not go through the Controller or Engine. They are queries, not mutations.

### 12.2 Operation Definition

Each operation is defined by:

```
IROperation
│
├── name: str
│       The operation name
│
├── inputs: Dict[str, TypeSpec]
│       Required parameters
│
├── preconditions: Set[Condition]
│       What must be true before the operation
│
├── effects: Set[Effect]
│       What the operation changes
│
├── postconditions: Set[Condition]
│       What must be true after the operation
│
└── invariants_preserved: Set[Invariant]
        Which invariants are guaranteed to hold after
```

### 12.3 Operations Are Not Mutations

| Concept | Definition | Authority |
|---------|------------|-----------|
| DNC-IR Operation | Abstract transformation vocabulary | Defined by specification |
| Mutation Proposal | Proposed application of operations | Computational Generator |
| Mutation Authorization | Approved proposal | Structural Controller |
| Mutation Transaction | Atomic application of authorized operations | Mutation Engine |

This distinction preserves the six-role authority model from Q4.

## 13. Validation Rules

### 13.1 Validation Levels

| Level | When | What |
|-------|------|------|
| **Syntactic** | IR construction | Valid operation, valid parameters |
| **Semantic** | IR construction | Types match, contracts satisfied |
| **Structural** | After mutation | DAG property, connectivity, boundary |
| **Invariant** | After mutation | All invariants hold |
| **Constraint** | After mutation | All constraints satisfied |

### 13.2 Validation Pipeline

```
IR Operation
    │
    ├── Syntactic Validation
    │       "Is this a valid operation with valid parameters?"
    │
    ├── Semantic Validation
    │       "Do the types match? Are contracts satisfied?"
    │
    ├── Structural Validation
    │       "Is the resulting graph a DAG? Is it connected?"
    │
    ├── Invariant Validation
    │       "Do all invariants hold?"
    │
    └── Constraint Validation
            "Are all constraints satisfied?"
```

### 13.3 Validation Failure

| Failure Level | Response |
|---------------|----------|
| Syntactic | Operation rejected; cannot proceed |
| Semantic | Operation rejected or modified by Controller |
| Structural | Operation rejected; DAG property violated |
| Invariant | Operation rejected; system error |
| Constraint | Operation rejected or modified; Controller decides |

## 14. Serialization Requirements

### 14.1 Serialization Formats

DNC-IR must be serializable in multiple formats:

| Format | Purpose |
|--------|---------|
| **Canonical JSON** | Human-readable, debuggable, versionable |
| **Binary** | Efficient storage and transmission |
| **Database** | Persistent storage with query support |
| **Visualization** | Graphical representation for debugging |

### 14.2 Serialization Properties

| Property | Requirement |
|----------|-------------|
| **Completeness** | Serialization must capture all IR information |
| **Round-trip fidelity** | Deserialize(Serialize(graph)) == graph |
| **Stability** | Same graph always produces same serialization (for canonical format) |
| **Extensibility** | Unknown fields are preserved during round-trip |

### 14.3 Canonical Form

The canonical JSON serialization has a defined structure:

```json
{
  "dnc_ir_version": "1.0.0",
  "graph": {
    "id": "graph-uuid",
    "version": 17,
    "name": "my_computation",
    "units": { ... },
    "edges": [ ... ],
    "entry_points": [ ... ],
    "exit_points": [ ... ],
    "constraints": [ ... ],
    "metadata": { ... }
  }
}
```

The canonical representation is the **semantic model**, not any particular serialization:

```
DNC-IR Semantic Model (canonical)

    ├── Python Reference Implementation
    │       Canonical data structures
    │       Canonical validation

    ├── JSON Serialization

    │       Efficient
    │
    ├── Database Persistence
    │       Queryable
    │
    └── Visualization
```

### 15.2 Implementation Independence

The semantic model is independent of any implementation language. The Python reference implementation is one realization; other languages can implement the same semantics.

## 16. IR Versioning and Compatibility

### 16.1 IR Schema Versioning

The DNC-IR schema has its own version:

```
DNC-IR Schema Version: MAJOR.MINOR.PATCH
```

| Change | Version Bump | Compatibility |
|--------|-------------|---------------|
| New field added | MINOR | Backward compatible |
| Field removed or renamed | MAJOR | Breaking change |
| Bug fix in validation | PATCH | Compatible |

### 16.2 Graph Versioning

Each graph has its own version (see Section 7). This is separate from the IR schema version.

### 16.3 Version Negotiation

When loading a graph, the system checks:

1. Is the IR schema version compatible?
2. Can the current system read this version?
3. Are there unknown fields that need preservation?

## 17. Conformance Requirements

### 17.1 Conformance Levels

| Level | Requirements |
|-------|-------------|
| **Level 1: Structural** | Correct graph representation, valid edges, DAG property |
| **Level 2: Semantic** | Correct types, contracts, constraints |
| **Level 3: Identity** | Stable identity, version tracking, provenance |
| **Level 4: Mutation** | All operations produce valid graphs, invariants preserved |
| **Level 5: Full** | All of the above plus serialization round-trip fidelity |

### 17.2 Conformance Testing

A conformant implementation must:

1. Represent all graph elements defined in this specification
2. Preserve identity across mutations
3. Validate all constraints before declaring a mutation successful
4. Maintain invariant preservation guarantees
5. Support at least one serialization format with round-trip fidelity

**Composition with v1.x Execution Core**: DNC-IR Level 4 (Mutation Conformance) must ensure that mutations produce graphs satisfying the Execution Core's invariants (INV-1–9 from the Execution Core Freeze). DNC-IR conformance and v1.x Execution Core conformance compose: a fully conformant system satisfies both.

### 17.3 Conformance Declaration

An implementation declares conformance at a specific level:

```
DNC-IR Conformance Declaration
    Level: 5 (Full)
    Serialization: JSON, Binary
    Python Reference: 3.14+
```
